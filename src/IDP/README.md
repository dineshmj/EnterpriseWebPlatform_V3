# Identity Provider (Duende IdentityServer)

Signs people and services in for the whole platform and issues their tokens. Requirements and the client catalogue: [IDP-Requirements.md](../../doc/Requirements/IDP-Requirements.md).

## Security controls

What this project does to stay secure: each control, what would go wrong without it, the threat it stops, and where to find it in the code. The platform-wide picture: [Architectural and security features §2](../../doc/Architectural-And-Security-Features-Demoable-EWP-V3.md#2-security-features).

| # | Security control | If it were missing | Threat prevented | Where to look |
|---|---|---|---|---|
| 1 | Account lockout (5 failures → 15 minutes) and per-IP sign-in throttling | Passwords could be guessed endlessly | Brute force and credential stuffing (OWASP A07) | [UserRepository.cs](Repositories/UserRepository.cs), `AddRateLimiter` in [Program.cs](Program.cs) |
| 2 | Same time and message for an unknown user as for a wrong password (a dummy hash is verified) | An attacker could learn which usernames exist | Username enumeration | [UserRepository.cs](Repositories/UserRepository.cs), [PasswordManager.cs](Security/PasswordManager.cs) |
| 3 | Two-step sign-in (TOTP, RFC 6238) with encrypted secrets, hashed single-use recovery codes; `amr` in the tokens. Off in Development by default (`Mfa:Enabled`); outside Development the IDP refuses to start without it | A stolen password alone would open the account; a forgotten setting would silently switch MFA off in production | Account takeover; insecure defaults (OWASP A05) | [Totp.cs](Security/Totp.cs), [MfaService.cs](Security/MfaService.cs), [Mfa.cshtml.cs](Pages/Account/Mfa.cshtml.cs), [MfaSetup.cshtml.cs](Pages/Account/MfaSetup.cshtml.cs), `RequireMfaOutsideDevelopment` in [Program.cs](Program.cs) |
| 4 | Authorization code + PKCE only; no implicit or password (ROPC) grant; one-time refresh tokens (rotation) | Tokens in URLs; passwords handled by clients; a stolen refresh token usable forever | Token leakage and replay (RFC 9700) | [MfePayments.cs](ConfigRegistration/Clients/MFEs/MfePayments.cs) (and the other clients) |
| 5 | Token exchange (RFC 8693) by allow-list: who may exchange which token for which audience; the person is re-checked at every exchange | Any client could turn any token into a token for any API | Privilege escalation through delegation | [TokenExchangeGrantValidator.cs](Security/TokenExchangeGrantValidator.cs), `act` in [CustomProfileService.cs](Services/CustomProfileService.cs) |
| 6 | Client secrets from configuration, never compiled in; the development signing key only in Development | Secrets in the repository; a development key signing production tokens | Leaked secrets; forged tokens | [ClientSecretStore.cs](Security/ClientSecretStore.cs), [SigningCredentialExtensions.cs](Security/SigningCredentialExtensions.cs) |
| 7 | Operational store in PostgreSQL (refresh tokens hashed, details encrypted); key ring encrypted at rest, fail closed | A restart would sign everybody out; a database reader could use refresh tokens or read keys | Token theft from storage | `AddOperationalStore` in [Program.cs](Program.cs), [PersistentDataProtection.cs](../Common/WebUtilities/Security/PersistentDataProtection.cs) |
| 8 | Server-side sign-in sessions: each IDP session is a row in PostgreSQL (`identity_server."ServerSideSessions"`), the cookie only refers to it; sign-out deletes the row, and an expired session also ends the clients' sessions (back-channel logout) | The cookie would BE the session: a copy taken before sign-out (malware, a shared machine) would keep signing in as the person for up to 10 hours | Session replay after sign-out; stolen-cookie account takeover | `AddServerSideSessions<ServerSideSessionStore>` in [Program.cs](Program.cs), table in [IdentityAccessDb.sql](IdentityAccessDB/IdentityAccessDb.sql) |
| 9 | Security headers on every page: CSP without `'unsafe-inline'`, `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff` - with ONE exception: the authenticator-code page of a STEP-UP (a signed-in person, no password on it) may be framed by the Shell's origin only, for its in-page overlay | The sign-in page could be framed or carry injected script | Clickjacking and XSS on the sign-in page | [SecurityHeadersAttribute.cs](SecurityHeadersAttribute.cs) |
| 10 | Logout by POST; front-channel and back-channel logout to every client | A hostile link could sign people out; sessions would survive elsewhere | Logout CSRF; session reuse | [Logout.cshtml.cs](Pages/Account/Logout.cshtml.cs), [LoggedOut.cshtml](Pages/Account/LoggedOut.cshtml) |
| 11 | "Keep me signed in" lasts 8 hours, not 30 days | A sign-in would live for weeks on a shared or lost device | Session hijacking on unattended devices | `RememberLoginLifetime` in [PendingSignIn.cs](Security/PendingSignIn.cs) |
| 12 | Host filtering (`AllowedHosts`) and HSTS | A forged `Host` header could poison links in e-mails or discovery; HTTP downgrade | Host-header attacks; interception | [appsettings.Development.json](appsettings.Development.json), [Program.cs](Program.cs) |
| 13 | No authenticator code accepted twice, also under concurrency: each time step and each recovery code is claimed with ONE conditional database UPDATE (only the request that changed the row wins); wrong codes - at sign-in and during enrolment - are counted in one UPDATE towards the same lockout; once locked, the code page ENDS the half-finished sign-in and says the account is locked for 15 minutes (no further code is looked at) | Two simultaneous requests could both use the same code; enrolment codes could be guessed without limit; concurrent wrong codes could under-count | Replay of a one-time code; brute force of the second factor | `VerifyAsync`, `ConfirmEnrolmentAsync`, `CountFailureAsync` in [MfaService.cs](Security/MfaService.cs); `LockedOut` in [Mfa.cshtml.cs](Pages/Account/Mfa.cshtml.cs) |
| 13a | Client IDs and the web clients' addresses (redirect, logout and back-channel URIs) from configuration (`ClientIds`, `ClientBaseUrls`), https only; the client list is built at start-up, so a missing value stops the IDP | A redirect URI could be built from a stale or empty address; client IDs compiled into every component | Open redirect / token leakage through a wrong redirect URI; configuration drift | [ClientSettings.cs](Security/ClientSettings.cs), `appsettings.json` |
| 14 | Step-up without signing out: a client's request with `acr_values=mfa` (and `prompt=login`) for a person already signed in here asks ONLY for a fresh authenticator code - no password - and issues a new sign-in (new `auth_time`, `amr` mfa); anyone else signs in fully. The sign-in pages are never framed; only the step-up code page may be framed by the Shell (its in-page overlay), and in step-up mode it shows no link to the sign-in page | Approvers would have to sign out and in again before every risky action, or the freshness rule would be relaxed to avoid the friction | Stale sessions approving risky actions; workarounds that weaken MFA | `StepUpAcr` in [Login.cshtml.cs](Pages/Account/Login.cshtml.cs), [Mfa.cshtml.cs](Pages/Account/Mfa.cshtml.cs), `PendingSignIn.StepUp` |
| 15 | Customers are kept apart from staff: their own table (`customer_logins`), sign-in pages (`/Customer/*`) and clients (marked `ClientAudience.ForCustomers`). The profile service answers a customer client only from `customer_logins` (`name`, `customer_number` - no role, permission or branch) and a staff client only from `users`; a session of the other population is not active for the client, so Duende asks for a new sign-in on the right page; the staff page sends a customer client's request to the customer page and never completes it (and the reverse) | A customer sign-in could open a staff screen, or a staff session be reused by the customers' channel; a customer token could carry staff claims | Privilege escalation across populations; confused-deputy sign-in | [ClientAudience.cs](Security/ClientAudience.cs), [CustomProfileService.cs](Services/CustomProfileService.cs), [Login.cshtml.cs](Pages/Account/Login.cshtml.cs), [Customer/Login.cshtml.cs](Pages/Customer/Login.cshtml.cs) |
| 16 | The customers' channel (My EWP) on the FAPI 2.0 Security Profile: PAR required (`request_uri` 60 s), PKCE S256, `private_key_jwt` client authentication (ES256 public JWK only, read from `ClientKeys:<client id>`; a key file with a private part stops the start-up; the assertion's audience must be exactly this issuer), DPoP-bound access and refresh tokens (RFC 9449; each proof accepted once), ID tokens and the Journey API's access tokens signed PS256 (FAPI 2.0 does not allow RS256), 60-second codes, one-time refresh tokens, the IDP session reused for at most 15 minutes | The authorization request could be read or changed in the browser; a shared secret could leak; a stolen access or refresh token could be replayed from anywhere | Authorization request tampering; client impersonation; token theft and replay | [SelfServiceWeb.cs](ConfigRegistration/Clients/Customers/SelfServiceWeb.cs), [ClientKeyStore.cs](Security/ClientKeyStore.cs), `StrictClientAssertionAudienceValidation`, `AddJwtBearerClientAuthentication`, `AddDistributedMemoryCache` in [Program.cs](Program.cs), [SigningCredentialExtensions.cs](Security/SigningCredentialExtensions.cs) |
| 17 | DPoP along the customers' delegation chain: the My EWP BFF may exchange only a token bound to the very key it proves on that request (`cnf.jkt` = the proof's thumbprint); the Self-Service Journey API only a sender-constrained token the BFF exchanged for it, and every token it gets is bound to its own key; it may ask only for `accounts.customer.read` and `partner-products.customer.read` | A customer token copied from logs or memory could be exchanged by someone else; the Journey API could reach other data | Token replay through the exchange endpoint; lateral movement | `SenderConstrained` and the allow-list in [TokenExchangeGrantValidator.cs](Security/TokenExchangeGrantValidator.cs), [SelfServiceJourneyApiTokenExchange.cs](ConfigRegistration/Clients/M2M/SelfServiceJourneyApiTokenExchange.cs) |
| 18 | Online registration without giving anything away: the customer number and the e-mail on record, checked by Customer Onboarding (an onboarded customer without online access; one answer for every miss). Every outcome shows the same code page and words; on a miss a code row is made but no code is sent. The sign-in is created first (unique customer number), then Customer Onboarding links it; if that is refused or unreachable, the sign-in is removed again. The IDP asks as itself: a 60-second token it signs in-process for a pseudo-client with no secret anywhere (`IdentityServer.CustomerDirectory.ClientID`, scope `customer-onboarding.online-identity`) | The page would tell a stranger which customer numbers and e-mail addresses are real, or who already registered; half-finished registrations could leave orphans; a shared secret for the IDP's own call could leak | Account enumeration (OWASP A07); account takeover by registering first | [Register.cshtml.cs](Pages/Customer/Register.cshtml.cs), [Code.cshtml.cs](Pages/Customer/Code.cshtml.cs), [CustomerDirectory.cs](Customers/CustomerDirectory.cs) |
| 19 | Customers' one-time codes (registration; the second factor while `Mfa:Enabled`): six random digits, 5 minutes, 5 tries, accepted once by ONE conditional UPDATE; only a salted SHA-256 hash is stored; tries are counted on the row (the browser's encrypted cookie holds only the row's ID); a wrong sign-in code also counts towards the sign-in's lockout. The SMS is simulated: the console shows only the mobile's last three digits (the code only in Development), the page shows the code only while `CustomerSignIn:ShowCodesOnPage` is on, and the IDP refuses to start with that on outside Development | A short code could be guessed or replayed; a replayed cookie could buy fresh tries; codes could leak into production logs or pages | Brute force and replay of the second factor; secrets in logs | [CustomerOneTimeCodes.cs](Customers/CustomerOneTimeCodes.cs), [PendingCustomerCode.cs](Customers/PendingCustomerCode.cs), `SendCodeAsync` in [CustomerSignIn.cs](Customers/CustomerSignIn.cs), `ValidateOnStart` in [Program.cs](Program.cs) |
| 20 | Customer passwords: PBKDF2 (ASP.NET Core Identity's hasher), 12-128 characters and not containing the customer number (NIST: length, no composition rules); an unknown customer number costs the same work and gets the same answer; five wrong passwords or codes lock for 15 minutes (one UPDATE); no "keep me signed in" for customers | Weak passwords; customer numbers found by timing; endless guessing | Credential stuffing and brute force; enumeration | [CustomerLoginStore.cs](Customers/CustomerLoginStore.cs) |
| 21 | Behind an ingress that ends TLS: `X-Forwarded-For` / `X-Forwarded-Proto` are applied only from the proxies listed under `ForwardedHeaders:KnownNetworks` / `KnownProxies` (one hop; the Host header is never taken from a forwarded header); nothing listed (local runs) = none trusted | Trusting the headers from anyone would let a caller fake its address (rate limits, logs) or the scheme; trusting none behind an ingress would produce http:// sign-in redirects and endpoints | IP and scheme spoofing (CWE-348); misconfiguration (OWASP A05) | [ProxyForwardedHeaders.cs](../Common/WebUtilities/Security/ProxyForwardedHeaders.cs), `UseEwpForwardedHeaders` in [Program.cs](Program.cs) |
| 22 | Container image: built only by CI from a commit, chiseled non-root runtime, base images pinned by tag and digest, scanned before it is published; NO key material inside - the token-signing certificate, the private_key_jwt clients' public keys and every client secret are mounted or set at run time (`.dockerignore` keeps `tempkey*.jwk`, `keys/` and `appsettings.Development.json` out); the identity database's connection string is no longer in `appsettings.json` | A signing key in a published layer lets anyone who pulls the image mint tokens for every API | Token forgery; hard-coded credentials (CWE-798, CWE-321); supply-chain tampering (OWASP A08) | [Dockerfile](Dockerfile), [.dockerignore](../../.dockerignore), [container-images.yml](../../.github/workflows/container-images.yml), [doc/Containers.md](../../doc/Containers.md) |
| 23 | One-time proofs stay one-time across every IDP instance: the replay cache for DPoP proofs and `private_key_jwt` client assertions (their `jti`) is in the IDP's PostgreSQL database (`identity_server.replay_cache`, only a SHA-256 of the `jti`, until the proof expires), not in one instance's memory | With several instances behind one address, a proof already used at one instance would be accepted again at another within its lifetime | Replay of a DPoP proof or a client assertion (RFC 9449 §11.1, RFC 7523 §3) | [DatabaseReplayCache.cs](Security/DatabaseReplayCache.cs), [IdentityAccessDb.sql](IdentityAccessDB/IdentityAccessDb.sql) |
| 24 | The cloud demo's Grafana is a client ONLY where it exists (`ClientBaseUrls:Grafana` set: the EWP chart with `global.observability.enabled`): Authorization Code + PKCE, its own https callback only, scopes `openid profile roles` - no API scope, no token exchange, no refresh token; its secret like every client's (`ClientSecrets:Grafana.ClientID`, Key Vault in the demo). Grafana admits only operations and platform administrators by the role claim | Grafana would need its own login (a password outside MFA, lockout and audit), or an unused client would wait in every environment | Credential sprawl; an unused client as an attack surface (OWASP A07) | [ObservabilityGrafana.cs](ConfigRegistration/Clients/ObservabilityGrafana.cs), `GetClients` in [Config.cs](Config.cs) |

**Not yet:** passkeys / FIDO2 (phishing-resistant sign-in).
