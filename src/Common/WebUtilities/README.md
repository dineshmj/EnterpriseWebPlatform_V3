# Common.WebUtilities

Shared web security building blocks for the BFFs and APIs.

## Security controls

What this project does to stay secure: each control, what would go wrong without it, the threat it stops, and where to find it in the code. The platform-wide picture: [Architectural and security features §2](../../../doc/Architectural-And-Security-Features-Demoable-EWP-V3.md#2-security-features).

| # | Security control | If it were missing | Threat prevented | Where to look |
|---|---|---|---|---|
| 1 | Content-Security-Policy builder: scripts and styles by SHA-256 hash of the exported inline blocks, computed at start-up; no `'unsafe-inline'` | Each BFF would hand-write its policy, and inline code would need `'unsafe-inline'` | Cross-site scripting and CSS injection (OWASP A03) | [ContentSecurityPolicy.cs](Security/ContentSecurityPolicy.cs) |
| 2 | Data Protection keys in PostgreSQL, encrypted at rest (certificate, or DPAPI in Development); no protection configured = no start | Keys in plain files or memory: readable by anyone with the database, lost on restart | Cookie forgery; sign-out of everyone on restart | [PersistentDataProtection.cs](Security/PersistentDataProtection.cs) |
| 3 | Per-caller rate limiting (person by `sub`, machine by `client_id`, anonymous by IP), 429 with `Retry-After` | One shared bucket, or none: a single caller could exhaust a service | Unrestricted resource consumption (OWASP API4) | [RateLimiting.cs](Security/RateLimiting.cs) |
| 4 | MFA step-up requirement (`amr` must contain `mfa` and `auth_time` must be recent), 403 `mfa_required` with a clear reason (the screens then ask for a fresh code in the Shell's in-page overlay) | Risky decisions would need only a password | Account takeover leading to fraudulent decisions | [MfaStepUp.cs](Security/MfaStepUp.cs) |
| 5 | Deny by default for the domain APIs: `MapEwpApiControllers` (an authenticated caller on every controller, plus the given policies) and `DenyAnonymousByDefault` (fallback policy for any endpoint without its own) | Each API would protect its endpoints its own way; one forgotten line would leave a new controller public | Broken function-level authorization (OWASP API5) | [ApiEndpointAuthorization.cs](Security/ApiEndpointAuthorization.cs) |
| 6a | Internal addresses and client IDs from configuration only (`RequiredSetting`: missing = no start-up, addresses absolute https; `ClientIds`: each API pins only the client IDs it names in `ClientIds:<client>`, read at start-up) - no compiled-in defaults | A component would fall back to a stale compiled-in address or an empty client pin | Tokens sent to the wrong place; an authorization pin matching nothing or the wrong client | [RequiredSetting.cs](Configuration/RequiredSetting.cs), [ClientIds.cs](Configuration/ClientIds.cs) |
| 6 | External-system addresses checked at start-up (absolute, no credentials; outside Development https, `PermittedHosts`, no loopback / private / link-local address) and `WithoutRedirects` for their clients | A wrong or tampered address would receive API keys and customer data | Server-side request forgery by configuration (CWE-918) | [ExternalEndpoint.cs](Security/ExternalEndpoint.cs) |
| 7 | Forwarded headers (`UseEwpForwardedHeaders`): `X-Forwarded-For` / `X-Forwarded-Proto` only from the proxies listed under `ForwardedHeaders` (CIDR networks or IPs, one hop), never the Host; nothing listed = none trusted; an invalid entry stops the start-up | Behind a TLS-ending ingress the IDP and BFFs would build http:// addresses; trusting the headers from anyone would let a caller fake its IP (rate limits, logs) or the scheme | IP and scheme spoofing (CWE-348); misconfiguration (OWASP A05) | [ProxyForwardedHeaders.cs](Security/ProxyForwardedHeaders.cs) |
| 8 | The MFE's Shell origin at run time (`MapEwpMfeRuntimeConfig`): `/ewp-runtime-config.js` from the BFF's validated `ShellOrigin` setting, JSON-encoded, frozen, not cached, anonymous (no secret) | Built into the front end, the origin would tie each image to one environment; built from the request it could be steered by an attacker | Cross-origin message spoofing (CWE-346) | [MfeRuntimeConfig.cs](Security/MfeRuntimeConfig.cs) |
| 9 | Next.js 16 export prefetch files (`UseEwpNextExportSegmentFiles`): a missing `__next.a.b.__PAGE__.txt` is served from the nested `__next.a/b/__PAGE__.txt` the export writes - only when that file exists in wwwroot, only segments of letters, digits, `_` and `-` | Every prefetch would answer 404 (console errors, data loaded again); a loose rewrite could map a request outside the exported files | Path traversal (CWE-22) avoided by construction | [NextExportSegmentFiles.cs](Helpers/NextExportSegmentFiles.cs) |
| 10 | A dependency's outage answered at once (`DependencyOutage`): connection strings get a 5-second connect timeout unless they set `Timeout` (`FailFast`); `UseEwpOutageAnswer` turns ONLY "a dependency is unavailable" - the database (Npgsql connection failure; server shutting down, starting up, out of connections), the sign-in against the IDP (PAR, discovery), an HTTP dependency unreachable / timing out / answering 502-504 - into 503 + `Retry-After: 15` - a self-reloading page without script or inline style for a page load, Problem Details for a call; trace ID only. Every other error keeps its handling | A white frame for 15 s, then a raw error page that may show internals; callers waiting for nothing | Information disclosure through error pages (OWASP A05); availability | [DependencyOutage.cs](Resilience/DependencyOutage.cs) |
