# BSS Shell (BFF + Next.js host)

The business-neutral host: signs the person in, shows the menu their roles allow, frames each context's MFE and shows notifications.

## Security controls

What this project does to stay secure: each control, what would go wrong without it, the threat it stops, and where to find it in the code. The platform-wide picture: [Architectural and security features §2](../../doc/Architectural-And-Security-Features-Demoable-EWP-V3.md#2-security-features).

| # | Security control | If it were missing | Threat prevented | Where to look |
|---|---|---|---|---|
| 1 | Tokens stay on the server (Duende BFF); the browser holds only an HttpOnly session cookie, and the Shell attaches the token to the Notifications calls it proxies | Any XSS bug could read the tokens | Token theft (OWASP A07) | `AddBff`, the Notifications proxy in [Program.cs](Program.cs) |
| 2 | Session cookie `__Host-`, HttpOnly, Secure, `SameSite=Lax`, 30 minutes sliding; sessions and key ring in PostgreSQL (`shell_bff`), key ring encrypted at rest | Cookie readable by script or sent cross-site; restart signs everyone out; stolen key ring forges cookies | Session theft, CSRF and session forgery | `AddCookie` in [Program.cs](Program.cs), [PersistentDataProtection.cs](../Common/WebUtilities/Security/PersistentDataProtection.cs), [EwpBffStateDb.sql](../../db/EwpBffStateDb.sql) |
| 3 | Duende's anti-forgery header on every `/bff` API call (`UseBff` before `UseAuthorization`) | A hostile page could call the Shell's API with the user's cookie | Cross-site request forgery | `UseBff` in [Program.cs](Program.cs); [auth.ts](client-app/app/lib/auth.ts) |
| 4 | The notifications WebSocket accepts only the Shell's own origin (a browser cannot add the anti-forgery header to a WebSocket upgrade) | Another site could open the hub with the user's cookie and read their notifications | Cross-site WebSocket hijacking | Origin check before the hub in [Program.cs](Program.cs) |
| 5 | Strict Content-Security-Policy (scripts and styles by hash, no `'unsafe-inline'`); `frame-src` limited to the MFEs and the IDP | Injected scripts or styles would run; the Shell could be made to frame any site | Cross-site scripting, CSS injection, framing of hostile content | [ContentSecurityPolicy.cs](../Common/WebUtilities/Security/ContentSecurityPolicy.cs), `ContentSecurityPolicy.Build` in [Program.cs](Program.cs) |
| 6 | Never framed: `frame-ancestors 'none'` and `X-Frame-Options: DENY` - except the static step-up done page (`/step-up-done.html`, no script, no data), which only the Shell itself may frame (`'self'`, `SAMEORIGIN`) | Another site could overlay the Shell to trick a click | Clickjacking | Security-header middleware in [Program.cs](Program.cs) |
| 6a | Step-up in an in-page overlay instead of a pop-up: only for the accepted application in the frame (origin and window checked, a request ID); the overlay frames THAT origin's fixed `/api/auth/step-up?in=shell` (nothing else from the message), ends on the Shell's own done page (readable only because it is the Shell's origin), answers `BSS_STEP_UP_RESULT` to that origin only; Cancel, Escape or 5 minutes close it unconfirmed; "use a separate window" as the fallback. The API checks the fresh MFA itself - the overlay only says "retry once" | Pop-up blockers stop the code prompt; a message could make the Shell frame any address | Blocked step-up; open framing / redirect | [StepUpOverlay.tsx](client-app/app/components/StepUpOverlay.tsx), `BSS_STEP_UP_REQUEST` in [page.tsx](client-app/app/page.tsx) |
| 7 | Messages from a frame accepted only from that frame's window AND from the origin of the MFE the Shell itself loaded (taken from the menu's address, never from the message); messages to an MFE sent to that origin only | A frame navigated to another site keeps the same window: it could announce itself as ready and receive the workspace context and notifications | Cross-origin message spoofing and data leakage | `expectedFrameOriginRef` in [page.tsx](client-app/app/page.tsx) |
| 8 | Menu built on the server from the person's role claims; every controller requires a signed-in user | Menu data would be served to anyone | Information disclosure; but note that the menu is not authorization: every API checks again | [MenuController.cs](Controllers/MenuController.cs), [MenuRepository.cs](Data/MenuRepository.cs) |
| 9 | No inline styles: the sign-in spinner and the not-found page are styled by class | The CSP would need `'unsafe-inline'` for styles | CSS injection | [AuthGuard.tsx](client-app/app/components/AuthGuard.tsx), [not-found.tsx](client-app/app/not-found.tsx), [globals.css](client-app/app/globals.css) |
| 10 | `nosniff`, referrer policy, HSTS, host filtering, per-caller rate limits | MIME sniffing, URL leakage, HTTP downgrade, host-header attacks, floods | Several smaller browser and transport attacks; resource exhaustion | [Program.cs](Program.cs), [RateLimiting.cs](../Common/WebUtilities/Security/RateLimiting.cs), [appsettings.Development.json](appsettings.Development.json) |
| 11 | A notification opens only a page path of the form `/v1/<area>/<page>` with at most ONE parameter (a numeric id or an upper-case reference such as `APP-20261012-000001`), and only through a microservice in the person's own menu; that BFF's allow-list checks the exact shape again | A notification's stored target could send the person to another site, or carry script, encoded text or extra parameters into a page | Open redirect and injection through stored notification targets | `OPENABLE_PATH`, `openablePath` in [notifications.ts](client-app/app/lib/notifications.ts); `ownerOf` in [page.tsx](client-app/app/page.tsx) |
| 12 | The Shell's own session (30 minutes) is renewed only by real activity: a click or key in the Shell, or `BSS_MFE_ACTIVITY` from the application in the frame (origin-checked, at most once a minute, no data); renewal at most every 5 minutes. Status checks while live updates reconnect pass `slide=false`, so they never keep an idle session alive. An ended session is shown as **Session ended** with **Sign in again** | The Shell's session ended unnoticed while the person worked inside an application, and live updates stayed "reconnecting" for ever; or a retry loop could keep an idle session alive | Session management: idle timeout (OWASP ASVS V3.3) | [session.ts](client-app/app/lib/session.ts), [useNotifications.ts](client-app/app/hooks/useNotifications.ts), [page.tsx](client-app/app/page.tsx) |
| 13 | Behind an ingress that ends TLS: `X-Forwarded-For` / `X-Forwarded-Proto` are applied only from the proxies listed under `ForwardedHeaders:KnownNetworks` / `KnownProxies` (one hop; the Host header is never taken from a forwarded header); nothing listed (local runs) = none trusted | Trusting the headers from anyone would let a caller fake its address (rate limits, logs) or the scheme; trusting none behind an ingress would produce http:// sign-in redirects and endpoints | IP and scheme spoofing (CWE-348); misconfiguration (OWASP A05) | [ProxyForwardedHeaders.cs](../Common/WebUtilities/Security/ProxyForwardedHeaders.cs), `UseEwpForwardedHeaders` in [Program.cs](Program.cs) |
| 14 | Container image: CI builds the Shell's front end from the committed lockfile (`--frozen-lockfile`) and the Shell from source - never a local export; chiseled non-root runtime; base images pinned by tag and digest, scanned before it is published; no client secret or password inside (the menu and BFF-state connection strings are no longer in `appsettings.json`; a missing one stops the start-up). The MFE addresses come from the menu database, not the image | A front end exported on a developer's machine could carry anything; a secret in a layer stays in the registry | Supply-chain tampering (OWASP A08); hard-coded credentials (CWE-798) | [Dockerfile](Dockerfile), [.dockerignore](../../.dockerignore), [container-images.yml](../../.github/workflows/container-images.yml), [doc/Containers.md](../../doc/Containers.md), [Program.cs](Program.cs) |
| 15 | One list of MFE addresses: `MfeOrigins` (configuration, https only, checked at start-up) is both the CSP's `frame-src` and the menu's source of addresses; the menu database names each MFE by key (`microservices.mfe_key`) and holds no address; a key without an address in this environment is left out of the menu and logged | Two hand-kept lists drift: the menu could send the browser to an MFE the CSP does not frame, or a database row could redirect the Shell to another site; and one environment's addresses would travel with the data | Misconfiguration (OWASP A05); open redirection through data | [MfeOrigins.cs](Configuration/MfeOrigins.cs), [MenuController.cs](Controllers/MenuController.cs), [EwpBssShellDb.sql](MenuDB/EwpBssShellDb.sql) |
