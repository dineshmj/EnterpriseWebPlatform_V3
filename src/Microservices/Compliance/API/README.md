# Compliance API

Compliance cases: AML / sanctions screening and the compliance officer's decision.

## Security controls

What this project does to stay secure: each control, what would go wrong without it, the threat it stops, and where to find it in the code. The platform-wide picture: [Architectural and security features §2](../../../../doc/Architectural-And-Security-Features-Demoable-EWP-V3.md#2-security-features).

| # | Security control | If it were missing | Threat prevented | Where to look |
|---|---|---|---|---|
| 1 | Strict access-token validation: issuer, audience, lifetime, signature against the IDP's keys, and only `typ: at+jwt` access tokens (RFC 9068); original claim names kept (`MapInboundClaims = false`) | A token issued for another API, an ID token or an expired token would be accepted | Token confusion and replay across APIs (OWASP API2 Broken Authentication) | `AddJwtBearer` in [Program.cs](Program.cs) |
| 2 | Deny by default, the same in every domain API: every controller needs an authenticated caller on top of its own policy, and any other endpoint without a policy needs one too (fallback policy); only health and metrics are explicitly anonymous | A new endpoint added without an attribute would be public | Broken function-level authorization (OWASP API5) | `MapEwpApiControllers`, `DenyAnonymousByDefault` in [Program.cs](Program.cs); [ApiEndpointAuthorization.cs](../../../Common/WebUtilities/Security/ApiEndpointAuthorization.cs) |
| 3 | Step-up: compliance decisions require a RECENT two-step sign-in (`amr` contains `mfa` and `auth_time` at most `Mfa:StepUpMaxAgeMinutes`, default 15, old) while `Mfa:Enabled` is on; outside Development the API refuses to start unless it is on | A stolen password alone would be enough to approve or reject; a session left open since a morning sign-in would still approve; a forgotten setting would silently switch the step-up off in production | Account takeover leading to fraudulent decisions; insecure defaults (OWASP A05) | [MfaStepUp.cs](../../../Common/WebUtilities/Security/MfaStepUp.cs), `stepUpPolicies` and `RequireMfaOutsideDevelopment` in [Program.cs](Program.cs) |
| 4 | Officer attributes (role, department, branch) checked per request; branch-scoped reads | Any signed-in person, or another branch's officer, could read or decide cases | BOLA and excessive privilege (OWASP API1, API5) | [ComplianceOfficerAuthorization.cs](Authorization/ComplianceOfficerAuthorization.cs) |
| 5 | Clearance by the case's risk: LOW 3, MEDIUM 4, HIGH 5 (in the aggregate) | A junior officer could clear a sanctions match | Inappropriate approval of high-risk customers | `RiskPolicy` in [ComplianceCodes.cs](Domain/ValueObjects/ComplianceCodes.cs), `Approve` in [ComplianceCase.cs](Domain/Aggregates/ComplianceCase.cs) |
| 6 | Cross-context separation of duties: neither the initiator nor a KYC decider of the same application may act | One person could verify a customer and clear them for financial crime | Collusion-free insider fraud | `EnsureOfficerMayAct` in [ComplianceCase.cs](Domain/Aggregates/ComplianceCase.cs) |
| 7 | A screening failure is never a pass; the provider is called with an API key, timeouts and a circuit breaker | An outage of the provider could let customers through unscreened | Fail-open AML / sanctions screening | `RecordScreeningFailure` in [ComplianceCase.cs](Domain/Aggregates/ComplianceCase.cs), [ScreeningProviderClient.cs](Infrastructure/Screening/ScreeningProviderClient.cs) |
| 8 | Internal endpoints accept only the one machine client meant to call them (`client_id` pinned, not just the scope) | Any service holding the scope could post fake workflow steps (e.g. a forged "KYC approved" message) | Service impersonation and spoofed workflow events | Policy `ComplianceCaseOpeningSubscriberWrite` in [Program.cs](Program.cs); [InternalComplianceCasesController.cs](Controllers/InternalComplianceCasesController.cs) |
| 9 | Problem responses without internals (a `traceId` only; details are logged on the server) | Stack traces, SQL or exception messages would reach the caller | Information disclosure that helps an attacker (CWE-209, OWASP A05) | [ApiExceptionHandler.cs](Controllers/ApiExceptionHandler.cs) |
| 10 | Per-caller rate limits (person, machine client, IP), 429 with `Retry-After`; the subscribers' internal endpoints too (machine-client budget); counted per instance (R-14) | One caller, or a stolen token, could flood the API for everybody | Unrestricted resource consumption (OWASP API4) | [RateLimiting.cs](../../../Common/WebUtilities/Security/RateLimiting.cs), `AddEwpRateLimiting` in [Program.cs](Program.cs) |
| 11 | Own least-privilege database user `ewp_compliance_api`: its own database only, no DDL | A compromised API or leaked connection string would expose other contexts' data or let the schema be changed | Lateral movement and blast radius of a breach | [EwpServiceDbUsers.sql](../../../../db/EwpServiceDbUsers.sql) |
| 12 | HTTPS only (HSTS outside Development) and host filtering (`AllowedHosts`) | Tokens could travel over plain HTTP; a forged `Host` header could poison generated links | Interception (OWASP A02) and host-header attacks | `UseHsts` in [Program.cs](Program.cs); `AllowedHosts` in [appsettings.Development.json](appsettings.Development.json) |
| 13 | The screening provider's address is checked at start-up: an absolute URL without credentials; outside Development https, a host listed in `ScreeningProvider:PermittedHosts`, and no loopback, private or link-local address; its client follows no redirects | A wrong or tampered address (e.g. a cloud metadata endpoint) would receive the API key and customer data; a redirect could move the call elsewhere | Server-side request forgery by configuration (CWE-918) | `ExternalEndpoint` in [Program.cs](Program.cs); [ExternalEndpoint.cs](../../../Common/WebUtilities/Security/ExternalEndpoint.cs) |
